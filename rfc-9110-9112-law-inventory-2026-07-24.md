(`local_3b9fdf15`) owns **layer placement, build-vs-adopt, package topology, the

## §1. Method — the positive control, and how the scan was run `[DONE]`

The lead flagged that a `CustomStringConvertible` change to HTTP Standard's
`Method` silently invalidated recorded corpora in three packages today, and
asked for the existence scan to be positive-controlled. Both are addressed here
— **and the flagged account turns out to be wrong as to cause; §1.1 corrects
it.**

**Positive control.** Every "absent/empty" result below was produced by a probe
shape that returns *non-zero* for a package known to be populated:
`swift-ietf/swift-rfc-5280/Sources` answered 62 source files under the identical
`find` invocation. A zero from this probe is therefore evidence of absence
rather than evidence of a mis-anchored path. This matters concretely: earlier in
the same session a probe rooted at the `swift-institute` workspace directory
returned a false negative because that directory is not itself a git repository
— the repository is the nested `Internal/`. Roots used here:
`swift-ietf/` for the `swift-rfc-*` family and `swift-standards/` for the
`-standard` suffix family, which are **different families**, not nested ones.

**Where `Method` actually lives.** There is exactly one declaration, and the
apparent second one is a re-export:

- Declared at `swift-ietf/swift-rfc-9110/Sources/RFC 9110/HTTP.Method.swift:32`
  as `public struct Method: Hashable, Sendable, Codable, RawRepresentable`,
  nested to `RFC_9110.Method`.
- `CustomStringConvertible` conformance at the same file, line 214. This was
  initially reported as the surface whose *change* invalidated three packages'
  corpora; **that attribution is wrong — see §1.1**, which supersedes it. The
  conformance has been unchanged since 2025-11-16.
- `swift-standards/swift-http-standard/Sources/HTTP Standard/exports.swift`
  contains only `@_exported public import RFC_9110` (plus 9111 and 9112). So
  "HTTP Standard's `Method`" *is* `RFC_9110.Method`, reached through an umbrella.

**Ruling this implies for §2:** `Method` is a **foundation, not a duplicate**.
There is one type.

### 1.1 CORRECTION — the corpus invalidation was not caused by a rendering change `[DONE]`

An earlier revision of this document (v0.1.0) repeated the standing account that
a `CustomStringConvertible` change to `Method` invalidated three packages'
corpora on 2026-07-24. **That account is wrong as to cause, and this section
supersedes it.** The HTTP-stack lane challenged it; I verified independently
rather than swapping one unverified story for another. Evidence:

- The `CustomStringConvertible` conformance entered at **`bba4de9`,
  2025-11-16** ("feat: initial implementation of RFC 9110") — established by
  pickaxe (`git log -S 'CustomStringConvertible'`) over the file. It is eight
  months old, not one day old.
- `swift-rfc-9110` has **no commit on 2026-07-24**. Repository HEAD is
  `7f79077`, dated **2026-07-10**. The most recent touch to `HTTP.Method.swift`
  is `11b3328`, **2026-07-08**, a mechanical lint drain.

So the rendering did not change that day. What changed was **consumer
resolution**: consumers resolve these packages at local committed HEAD through a
1,256-entry mirror map with **no version gate**, so a long-committed rendering
reached three consumers when their stale pins advanced (per the HTTP-stack
lane's survey: `swift-authentication`, `swift-stripe-types`,
`swift-identities-types`).

**Why the distinction is load-bearing and not pedantry.** The two accounts imply
different defects and different fixes:

| Account | Implied defect | Implied fix |
|---|---|---|
| "someone changed `description` today" | a careless API edit | a code-review rule about rendering changes |
| **actual: pins advanced onto an 8-month-old commit** | **unversioned resolution across the fleet** | **a version gate / pinning policy in the mirror map** |

The second is the more serious problem and the first fix would not touch it. A
rendering-change rule would have prevented nothing here, because there was no
rendering change.

**The transferable rule still stands, on its own merits** — `description` on a
spec type is load-bearing wire-adjacent API rather than a debugging affordance,
because recorded corpora and goldens bind to it — but it is a *standing hazard*,
not the *cause* of this incident.

**Method caveat, recorded honestly:** the HTTP-stack lane warns that
`git log --since=<bare ISO date>` silently returns zero for that day, and to use
an explicit time or relative window. I ran all three forms here; all three
returned zero. That agreement is **not** a positive control — with genuinely
zero commits in the window, every form returns zero and the degenerate case
proves nothing. The load-bearing evidence above is the pickaxe result and the
HEAD date, not the `--since` count. Their caveat should still be honoured
wherever a `--since` count is used as evidence.

### 1.2 The standing hazard, restated for §6 `[DONE]`

Given unversioned resolution, **any rendering or encoding change recommended by
this inventory goes live ecosystem-wide at each consumer's next resolve, with no
version boundary and no date stamp.** Recommendations of that kind must be
flagged individually and loudly rather than folded into a list. Carried into §6.

**Naming observation, not a defect.** File names use an `HTTP.` prefix
(`HTTP.Method.swift`, `HTTP.Status.swift`) while the types they declare nest
under `RFC_9110.*` / `RFC_9112.*`. The namespace enums are declared plainly
(`public enum RFC_9110 {}` at `RFC_9110.swift:29`; same shape for 9112, which
additionally does `@_exported import RFC_9110` so 9112 re-exports 9110's
surface). Flagging because a reader grepping for `HTTP.Method` finds a filename,
not a type; whether that is intentional is the HTTP lane's call, not mine.

**No filename collisions between 9110 and 9112** — the `comm -12` intersection of
their `HTTP.*.swift` file sets is empty. Type-level overlap is a separate check
still open (§2.2).

### 2.3 Obsoleted predecessors — RESOLVED: dead law `[DONE]`

`swift-rfc-7230` (1,370 lines) implements the *obsoleted* HTTP/1.1 syntax that
9112 replaces; `7231`–`7235` are near-empty stubs (11–245 lines).

**Disposition (HTTP-stack lane, verified there): retirable.** The canonical
`swift-url-routing` has already migrated to `swift-http-standard` and references
the 723x family **zero** times; the only live edge is a stale duplicate checkout
under a workspace packages directory, sequenced behind a duplicate-checkout
cleanup. **Treat 7230 as dead law for inventory purposes.**

One live use remains for it, though: **salvage-before-retire.** If a 9112 clause
turns out to be implemented in 7230 and *not* in 9112, that is cheaper to lift
than to author.

**Salvage checked, result negative `[DONE]`.** The most promising lead was
Finding F (§3.8): since the trapping `[Byte]` line parsers have commented-out
bodies referencing a pre-Foundation-strip API, 7230 might have held a working
byte-level line parse. **It does not.** `swift-rfc-7230`'s six sources
(`HTTP.Version`, `Header.Field`, `Headers`, `Message.Request`,
`Message.Request.Target`, `RFC_7230`) contain **no `parse` entry point over
bytes at all**; `[Byte]` occurs only as a `body` payload type. Probe
positive-controlled — it reads 7230's own sources (21–22 `public` matches per
file).

One incidental observation, recorded to prevent a false match on a later sweep:
`HTTP.Version.swift:159` in 7230 contains a `fatalError`, but it is inside an
`ExpressibleByStringLiteral` initializer rejecting an invalid literal. That is
the conventional Swift idiom for literal validation and is **not** the Finding F
class — F is a runtime-reachable parse entry point over attacker-supplied bytes.
The distinction matters because a naive `grep fatalError` conflates them.

**Conclusion: 7230 offers no salvage for the framing redesign.** Retire it on
the schedule already set; no lines move from "rewrite" to "retain".

### 2.4 Verification items — ALL THREE CLOSED `[DONE]`

Resolved by the HTTP-stack lane with file-and-line evidence; recorded here
because each changes the inventory's shape.

**(a) 9110 ↔ 9112 type overlap — NO duplication; 9112 re-exports.**
`RFC_9112.swift:10` is `@_exported import RFC_9110`; `HTTP.Host.swift:4` is
`@_exported import RFC_3986`; `RFC_9111.swift:10` likewise re-exports 9110.
Types are re-exported, not redeclared, so there is no collision. **Two
consequences that matter more than the finding itself:**

1. `swift-http-standard`'s umbrella is **partly redundant** — `@_exported import
   RFC_9112` alone already supplies 9110.
2. ⚠️ **A consumer can bind 9110 types without naming `swift-rfc-9110` in its
   manifest.** Any consumer or conformance census over the HTTP law must chase
   **transitively re-exported symbols, not manifest edges** — a manifest-only
   census under-reports and will read as a clean, wrong answer.

This also widens *this* document's scope: because `@_exported` puts the 9110
surface in reach of every 9112 consumer, the smuggling-relevant **9110** clauses
(`Content-Length` field parsing, `Transfer-Encoding` field grammar) belong to the
framing half of the inventory even though they carry 9110 numbers.

**(b) Range requests, 9110 §14 — GENUINELY ABSENT, three ways.** No
`HTTP.Range*` file in `swift-rfc-9110`; only incidental matches (`If-Range` in
`HTTP.Precondition.swift`, field names in `HTTP.Header.Field.Name.swift`,
206/416 in `HTTP.Status.swift`). `swift-rfc-7233` (the obsoleted Range RFC) is an
11-line stub. `swift-http-range` (L3) is an empty scaffold — licence only.

**This is the largest single conformance hole in the 9110 surface.** It is also
not purely a 9110 concern: §14 interacts with 9112 §6.3, since a 206 response
with `Content-Range` participates in body-length determination. Recorded in both
halves.

**(c) `HTTP.Cache` — not an overlap; an empty namespace and a vocabulary trap.**
`HTTP.Cache.swift` declares `public enum Cache {}` and nothing else, with a
doc-comment deferring to RFC 9111. The real law lives at `RFC_9111.CacheControl`
(`HTTP.CacheControl.swift:53`) plus `Freshness`, `Age`, `Vary`, `Validation`,
`StorageEligibility`.

⚠️ Because `HTTP` is `typealias HTTP = RFC_9110`, a consumer writing
`HTTP.Cache.…` reaches **the empty enum**, while the law they want is at
`RFC_9111.CacheControl` — **not reachable through the `HTTP.` alias at all.**
Filed as a **namespace/vocabulary defect**, not a missing-law finding: the law
exists and is substantial, but the obvious spelling silently leads away from it.

### 2.5 Probe discipline for this inventory `[DONE]`

Two probe defects, both established by measurement in the HTTP-stack lane, each
of which produces **a clean zero indistinguishable from a true absence**. They
invalidated that lane's 7230 census twice, and the two uncorrected answers
pointed in *opposite* directions.

1. **zsh does not word-split unquoted parameter expansions.** With
   `R="/path/a /path/b"`, a `grep -r … $R` searches **nothing** — no stderr,
   exit 0. Use an array (`"${ROOTS[@]}"`), `${=R}`, or literal paths.
2. **Omitting `--exclude-dir='.build'`** lets `grep -r` descend into build trees
   and hit the timeout (exit 143), printing a partial result that also reads as
   a zero.

**Standing rule adopted for every probe in this document:** control each probe at
its degenerate case — confirm it *finds a surface already read by hand* before
trusting a zero from it. §1 records the instance of this rule that caught a
false negative here; §1.1 records an instance where a control was **degenerate
and therefore proved nothing**, which is the failure mode one step subtler than
having no control at all.

## §3. The parsing-hazard clauses — §6.3 read against the shipped code `[DONE]`

This is the section the lead named as the priority, and it is where the
inventory stops being a catalogue. **Five findings, four of them
smuggling-relevant.** Each is classified per the HTTP-stack lane's request:

- **MISSING CHECK** — the law is unimplemented but *implementable* within the
  current API shape.
- **WRONG DISPOSITION** — the condition *is* detected, but the outcome violates
  the clause. Worse than missing, because it looks handled.
- **STRUCTURAL** — the clause cannot be satisfied by a whole-buffer API at all;
  no amount of checking fixes it.

### 3.1 The law being checked against

RFC 9112 §6.3 is an *ordered* algorithm, and three of its rules are the
smuggling surface:

- **Rule 3 (TE over CL).** Transfer-Encoding overrides Content-Length. A message
  bearing both "might indicate an attempt to perform request smuggling … and
  ought to be handled as an error"; a forwarding intermediary **MUST** first
  remove the Content-Length.
- **Rule 3, chunked-not-final.** If Transfer-Encoding is present in a **request**
  and chunked is not the *final* coding, the body length cannot be determined
  reliably and the server **MUST** respond 400 and close the connection. In a
  **response**, the same condition means read-until-close. Note the two sides
  differ — a single shared code path cannot be correct for both.
- **Rule 5 (invalid CL).** A message without Transfer-Encoding and with an
  invalid Content-Length — including multiple fields with differing values, or
  one field holding a differing comma-separated list — has invalid framing, and
  the recipient **MUST** treat it as an unrecoverable error.

### 3.2 FINDING A — invalid framing is reported as "no body" `[WRONG DISPOSITION]`

`HTTP.MessageBodyLength.calculate` detects both invalid-Content-Length cases and
then returns **`.none`** for each of them:

- multiple differing Content-Length values → `return .none` (response path and
  request path both)
- unparseable / negative Content-Length → `return .none`

`.none` is the same value returned for a legitimately body-less message. So a
message with **invalid framing is reported as valid with an empty body**, and
whatever bytes follow in the buffer are then interpreted as *the next message*.
That is the CL-desync smuggling primitive, reached through the exact path the
clause exists to prevent.

The root cause is at the type level, which is why this is not a one-line fix:

```
public enum MessageBodyLength { case none, length(Int), chunked, untilClose }
public static func calculate(...) -> Self          // non-throwing
```

There is **no case that can express "invalid framing"** and no error channel.
Invalid input has nowhere to go *except* `.none`. Fixing this means adding a
rejection case or making `calculate` throwing — an API-breaking change, and per
§1.2 an API change here lands ecosystem-wide at each consumer's next resolve.

### 3.3 FINDING B — chunked-not-final is not detected, and the correct predicate already exists unused `[MISSING CHECK]`

`calculate` gates on `TransferEncoding.hasChunked`, which is **membership**:

```
public var hasChunked: Bool { encodings.contains { $0.isChunked } }   // :189
```

`Transfer-Encoding: chunked, gzip` — chunked present but **not final** — therefore
frames as chunked, when §6.3 requires 400-and-close on the request side.

The sharp part: **`TransferEncoding` already ships the correct finality-aware
accessor**, documented in its own source as *"Returns true if chunked is the
final encoding … Per RFC 9112, chunked MUST be the final encoding when present"*
(`HTTP.TransferEncoding.swift:198-200`). The right predicate is in the same
file as the wrong one. This is a call-site defect, not a missing capability —
cheap to fix, and the cheapest real security win in the inventory.

### 3.4 FINDING C — TE + CL coexistence is never signalled `[MISSING CHECK]`

`calculate` returns `.chunked` on seeing Transfer-Encoding and never looks at
whether Content-Length was *also* present. The caller therefore cannot know the
message bore both. Consequences: the "ought to be handled as an error" server
disposition is unavailable, and the **MUST** on intermediaries to strip
Content-Length before forwarding cannot be complied with, because the fact is
not reported. Any proxy built on this type is non-conformant by construction.

### 3.5 FINDING D — chunked consumed-count is estimated from decoded size `[STRUCTURAL]`

`HTTP.Message.Deserializer.swift:119` carries a self-admitted defect in shipped
source:

```
// Calculate chunked bytes consumed (this is approximate - should track precisely)
// For now, we'll use the decoded data size as estimate
bytesConsumed += chunkedData.count
```

Decoded size is **not** consumed size: chunked framing adds per-chunk size
lines, CRLF delimiters, the terminating zero chunk and any trailer section. The
count is therefore short by a message-dependent amount, so after a chunked
message the deserializer's idea of where the *next* message begins is wrong. On
a reused or pipelined connection that is a desync — the same primitive as
Finding A, reached from the chunked side.

"Inexact consumed count" is already a **named N7 STOP condition** in
`Research/native-networking-wave-3-implementation-heritage-dependency-record.md:769`,
so this is a known-and-accepted blocker rather than a discovery — but it is now
localised to one line, which it was not before.

Classified structural rather than missing because the surrounding API has no
consumed-count contract to be correct *against* (§3.6); tracking precisely means
introducing that contract.

### 3.6 FINDING E — the API is whole-buffer only `[STRUCTURAL]`

Confirmed independently by the HTTP-stack lane's survey: `parseLines(from data:
[Byte]) -> [Line]` and static `deserialize(…)` take a complete buffer. There is
no resumable state, no "need more bytes" signal, and no consumed count in the
contract. The heritage record states the same conclusion at `:119` — *"RFC 9112
is whole-buffer only and is not safe as a bounded reusable socket drive."*

Whole classes of MUST-law are therefore **unsatisfiable rather than
unimplemented**, and should be sized as redesign, not as checks to add:

- incremental framing across partial reads
- bounded field/line/body limits enforced *during* parse (a whole-buffer parser
  has already accepted the bytes before it can object)
- partial-IO resumption on a reused connection
- any correct consumed-count contract (Finding D depends on this)

### 3.8 FINDING F — two public API entry points are `fatalError("Not implemented")` in shipped source `[DEFECT — not a conformance gap]`

Found while sanity-checking the salvage boundary (§3.9). This is not a missing
check or a wrong disposition; it is **public API that terminates the process**:

```
HTTP.Request.Line.swift:73    public static func parse(_ data: [Byte]) -> Self { fatalError("Not implemented") }
HTTP.Response.Line.swift:85   public static func parse(_ data: [Byte]) -> Self { fatalError("Not implemented") }
```

In both, the real implementation is present but commented out, referring to a
`String(data:encoding:)` API that the Foundation strip removed. The `String`
overloads (`parse(_ line: String)`) are implemented and fine.

**Scope, positive-controlled and CORRECTED.** An earlier revision reported
"9112 has two, 9110 has zero." That was true only of the keyword `fatalError`.
Widening the probe family to
`fatalError|preconditionFailure|try!|as!|unsafelyUnwrapped` across the chain
(control: the probe finds `Request.Line.swift:73`, already read by hand):

| Package | Count | Sites |
|---|---:|---|
| `swift-rfc-9112` | 2 | `Request.Line.swift:73`, `Response.Line.swift:85` — Finding F |
| `swift-rfc-9110` | 1 | `HTTP.Request.swift:148` — `try! RFC_3986.URI.Path("/")` |
| `swift-rfc-9111` | 0 | clean |

**The 9110 site is a robustness item, not a security finding** — stated
precisely because it sits in the most-consumed package in the chain. It is a
non-throwing public initializer applying `try!` to the *constant* `"/"`;
`URI.Path.init` is throwing, but `"/"` is a valid path, so it cannot trap in
practice. The source carries `// swiftlint:disable:next force_try`, so it was a
known, accepted shortcut. Correct fix is a validated `static let` built once.
Recorded so that §5's strength classification does not inherit a "9110 is
trap-free" claim that holds only for one keyword. (Site identified by the
HTTP-stack lane; verified here.)

**Severity — CORRECTED, downward.** An earlier revision called Finding F a
remote DoS. **That overstates it, and the correction is load-bearing because the
claim will be read by people deciding urgency.** The HTTP-stack lane ran a
caller census across foundations/standards/ietf/repotraffic: **24 call sites of
`Request.Line.parse`/`Response.Line.parse`, every one passing a `String`** — 22
in 9112's own tests, plus two internal deserializer calls
(`Deserializer.swift:42`, `:233`). **The `[Byte]` overloads have zero callers,
so the trap is unreachable today.**

The accurate framing is therefore: **a trap laid directly across N7's path,
disarmable now at zero cost.** It becomes reachable the moment a redesigned
socket-driven parser calls the byte-level entry point — which is precisely what
N7 exists to build. Still Tier 0 (§6.0), but on *"cheapest possible win, do it
before it can bite"*, **not** on *"a remote DoS is shipping."*

Zero callers also makes deletion **zero-cost rather than a judgement call**:
there is no live caller to migrate, and any future caller is guaranteed to crash
today.

It remains invisible at the call site: the signature is total (`-> Self`,
non-throwing), so nothing suggests the call cannot return.

**Interaction with Finding A.** Note the signature these were *going* to have:
non-throwing `-> Self`, the same shape that forces Finding A's `.none` collapse.
Had they been implemented as written, malformed input would have had nowhere to
go. The correct fix is not to fill in the body but to give them a failure
channel — which makes them Tier-2 work (API-breaking), not Tier-1.

### 3.9 Salvage-boundary check — the HTTP lane's cut is right in outline, wrong at two points `[DONE]`

The HTTP-stack lane proposed retaining 9112's **declarative** law
(`HTTP.Version`, `Request.Line`, `Response.Line`, the validators,
`TransferEncoding`, `ChunkedEncoding` grammar) and replacing the
**message-driving** surface (`Parser.parseLines`, `Deserializer.deserialize`,
`MessageBodyLength.calculate`'s signature), and asked to be told early if any
declarative law turns out entangled with the whole-buffer assumption. Two are.

**Entanglement 1 — `ChunkedEncoding` is not cleanly retainable.** Its *grammar*
is (chunk-size line, extensions, trailer syntax). Its **API is the whole-buffer
assumption**:

```
public static func decode(_ data: [Byte]) throws -> DecodeResult          // :177
public struct DecodeResult { let data: [Byte]; let chunkExtensions: …; let trailers: … }   // :80
```

`DecodeResult` carries **no consumed count**. So Finding D is not a
`Deserializer` sloppiness that could be tightened in place — **the underlying
API cannot express the answer.** `Deserializer.swift:119` estimates from decoded
size because the type it calls gives it nothing better. Fixing D therefore
requires changing `DecodeResult`, which sits on the "retain" side of the
proposed boundary. **Move the `decode`/`DecodeResult` surface to the replace
side; keep the grammar.**

**Entanglement 2 — `Request.Line` / `Response.Line` are half-retainable.** The
`String` overloads are genuinely declarative and should be kept. The `[Byte]`
overloads are (a) unimplemented traps (§3.8) and (b) conceptually framing rather
than parsing — given raw bytes they must *find the line delimiter*, which is the
job the redesigned message-driving layer exists to own. **Keep the `String`
overloads; the `[Byte]` overloads belong to the replace side and should be
deleted rather than implemented.**

**Confirmed retainable, no entanglement found:** `HTTP.Version.parse(String)`,
`TransferEncoding.parse(String)` (header-value scoped),
`Request.Validator.validate(Request)` / `Response.Validator` (operate on already
-parsed messages). One caveat on `Request.Line.validate(maxLength: 8000)` at
`:91` — the bound exists but is a *separate call after* parsing, so it cannot
prevent over-long input from being accepted first. That is Finding E's DoS point
in miniature: a limit that is checkable only post hoc is not a limit.

**Net effect on N7 sizing:** the boundary moves in the direction that *increases*
rewrite, but only slightly and specifically — one result type plus two dead
overloads, not a category. The large declarative surfaces survive the cut.

### 3.7 Answer to the HTTP-stack lane's ask — MUST clauses an adopt-candidate must satisfy

Treat these as **disqualifiers, not caveats**. A candidate failing any of them
is not adoptable for N7:

1. **Invalid framing must be inexpressible as "no body."** The body-length result
   must carry a rejection outcome distinct from "legitimately empty" (Finding A).
2. **Chunked must be validated as the *final* coding**, with the request-side
   (400 + close) and response-side (read-until-close) dispositions distinguished
   (Finding B).
3. **TE + CL coexistence must be reported to the caller**, or intermediary
   conformance is impossible (Finding C).
4. **Exact consumed-byte count** across chunked bodies, including framing
   overhead and trailers (Finding D).
5. **Incremental, resumable parsing with bounded limits** — a whole-buffer-only
   API cannot drive a socket safely (Finding E).

Items 4 and 5 are the ones the *current* implementation fails structurally, and
they are also the ones most third-party HTTP/1.1 parsers get right, since a
socket-driven parser cannot function without them. That asymmetry is worth
weighing in the build-vs-adopt call: the existing tree is strong on
**semantics** (9110 is 5,916 lines of it) and structurally weak on **framing**.

## §4. Where byte fixtures are needed `[DONE]`

### 4.1 The idiom, carried from the rfc-5280 lane

Two rules, both learned by having them matter:

1. **Pin the rule, not the instance.** Use two distinct instances that differ in
   the dimension the rule ranges over, so the fixture constrains the *class*. In
   rfc-5280 that meant asserting the implicit-tag encoding at two different tag
   numbers rather than one.
2. **Pin both directions.** Assert the accepted encoding *and* the encoding that
   MUST be rejected. This is the load-bearing half: **a round-trip test
   structurally cannot produce an illegal encoding, and therefore cannot detect
   that the parser accepts one.** Every §3 finding here is an
   accepts-what-it-must-reject defect, which is exactly the class round-trips
   are blind to.

HTTP makes this sharper than DER did. DER illegality is mostly malformity; HTTP
illegality is mostly **ambiguity** — two framings disagreeing about where a
message ends. The fixture must therefore assert *rejection*, not merely that
some parse happened.

### 4.2 Framing fixtures — the smuggling set

Each entry: the wire bytes, the clause, and the required disposition. These are
the fixtures whose absence lets §3's findings exist.

| # | Fixture (CRLF shown as `\r\n`) | Clause | Required disposition |
|---|---|---|---|
| F1 | `Content-Length: 5\r\nContent-Length: 6\r\n` | 9112 §6.3 r5 | **REJECT** — unrecoverable. Currently `.none` (Finding A) |
| F2 | `Content-Length: 5\r\nContent-Length: 5\r\n` | 9112 §6.3 r5 | Accept as `.length(5)` — identical values are *not* the error case. Pairs with F1 to pin the rule rather than "two headers bad" |
| F3 | `Content-Length: 5, 6\r\n` | 9112 §6.3 r5 | **REJECT** — one field, differing list. Distinct code path from F1 |
| F4 | `Content-Length: abc\r\n` / `-1\r\n` / `+5\r\n` / `0x5\r\n` | 9112 §6.3 r5 | **REJECT** each. `+5` and `0x5` matter: `Int(…)`-style parsing accepts forms the ABNF (`1*DIGIT`) forbids |
| F5 | `Transfer-Encoding: chunked\r\nContent-Length: 5\r\n` | 9112 §6.3 r3 | TE wins **and the coexistence is reported** (Finding C). Intermediary MUST strip CL |
| F6 | `Transfer-Encoding: gzip, chunked\r\n` | 9112 §6.3 | Accept as chunked — chunked *is* final |
| F7 | `Transfer-Encoding: chunked, gzip\r\n` | 9112 §6.3 r3 | **Request: REJECT 400 + close. Response: read-until-close.** Two different dispositions from one input — F6/F7 together pin finality-not-membership (Finding B) |
| F8 | `Transfer-Encoding: chunked\r\n` on a **request**, vs on a **response** | 9112 §6.3 | Pins that request and response paths are *not* interchangeable |

### 4.3 Chunked consumed-count fixtures — the Finding D set

The defect is arithmetic, so the fixture must assert **the consumed count
itself**, not the decoded body. Decoded length is precisely the quantity that
looks right while being wrong.

| # | Fixture | Asserts |
|---|---|---|
| F9 | `5\r\nhello\r\n0\r\n\r\n` | decoded = 5 bytes; **consumed = 17 bytes.** A decoded-size proxy reports 5 — the fixture fails loudly on today's code |
| F10 | `5;ext=1\r\nhello\r\n0\r\n\r\n` | chunk extensions count toward consumed but not decoded |
| F11 | `5\r\nhello\r\n0\r\nX-Trailer: v\r\n\r\n` | trailer section counts toward consumed |
| F12 | two chunked messages back-to-back in one buffer | **the second parses correctly** — the end-to-end statement of Finding D. If the offset is wrong, message 2 is garbage or is silently a smuggled request |

F12 is the one to write first: it is the shortest expression of why the defect is
a security bug rather than an accounting nit.

### 4.4 Field-grammar fixtures — 9110 clauses reached through `@_exported`

Per §2.4(a) these are 9110-numbered but land in the framing half.

| # | Fixture | Clause | Disposition |
|---|---|---|---|
| F13 | `Host : example.com\r\n` (space before colon) | 9112 §5.1 | **REJECT 400.** Named anti-smuggling rule; classic request-splitting vector |
| F14 | `Content-Length:5\r\n` (no space after colon) | 9110 §5.6 | Accept — OWS is optional. Pairs with F13 so the fixture pins *which* whitespace is illegal |
| F15 | obs-fold: `X: a\r\n  b\r\n` | 9112 §5.2 | **REJECT** in requests (or replace with SP), never silently join |
| F16 | bare `\n` as terminator; bare `\r` inside a field | 9112 §2.2 | Bare CR **MUST NOT** be recognised as a terminator |

### 4.5 THE REJECT SET — gate criteria, separated from the accept set

Requested by the HTTP-stack lane as the Step 4 consumer-corpus gate criteria.
The separation matters for a specific reason: **Findings A, B, C and F are all
"detects or reaches the condition, then disposes of it wrongly," and a
happy-path corpus cannot catch any of them.** A corpus made only of
well-formed traffic will pass against defective code. These are the fixtures
that must **fail** today.

**REJECT SET — each MUST be refused; each currently is not**

| # | Input | Required refusal | Today |
|---|---|---|---|
| F1 | `Content-Length: 5` + `Content-Length: 6` | unrecoverable error | ✗ `.none` |
| F3 | `Content-Length: 5, 6` (one field) | unrecoverable error | ✗ `.none` |
| F4a | `Content-Length: abc` | unrecoverable error | ✗ `.none` |
| F4b | `Content-Length: -1` | unrecoverable error | ✗ `.none` |
| F4c | `Content-Length: +5` | unrecoverable error — `1*DIGIT` forbids the sign | ✗ likely accepted |
| F4d | `Content-Length: 0x5` | unrecoverable error | ✗ `.none` |
| F7r | `Transfer-Encoding: chunked, gzip` on a **request** | 400 + close | ✗ frames as chunked |
| F13 | `Host : example.com` (space before colon) | 400 | ⚠ unverified |
| F15 | obs-fold `X: a\r\n  b\r\n` in a request | reject or replace-with-SP | ⚠ unverified |
| F16 | bare `\r` as terminator | MUST NOT be recognised | ⚠ unverified |
| **F17** | **byte-level `Request.Line.parse([Byte])` on any input** | **must not terminate the process** | **✗ `fatalError` (§3.8)** |

**ACCEPT SET — each MUST be admitted; these exist to stop the reject set being satisfied by blanket rejection**

| # | Input | Required admission |
|---|---|---|
| F2 | `Content-Length: 5` + `Content-Length: 5` (identical) | `.length(5)` — duplicate-but-identical is legal |
| F6 | `Transfer-Encoding: gzip, chunked` | chunked framing — chunked *is* final |
| F14 | `Content-Length:5` (no space after colon) | legal — OWS is optional |
| F7s | `Transfer-Encoding: chunked, gzip` on a **response** | read-until-close, *not* an error |

**The accept set is not optional.** Without F2/F6/F14 a parser could pass the
entire reject set by rejecting everything adjacent to the hazard, and F7r/F7s
together are the only pair that proves request and response paths were
distinguished rather than unified into whichever disposition was easier.

**Consumed-count set — assert the count, never the decoded body** (§4.3): F9–F12,
with **F12** (two chunked messages back-to-back; the second must parse) as the
single most valuable gate entry, since it converts Finding D from an accounting
discrepancy into an observable smuggle.

### 4.6 Where these fixtures should live

Byte fixtures for framing belong beside the framing types (`swift-rfc-9112`),
not in a consumer. Two properties from the rfc-5280 experience are worth
preserving: they are **package-local**, so they gate at the owner's own test
target rather than at a downstream consumer's; and they are **plain byte
arrays**, so they survive refactors of the types they constrain. Note the
interaction with §1.2: fixtures asserting *rendering* would be subject to the
unversioned-resolution hazard, but fixtures asserting *wire acceptance and
rejection* are exactly what makes such a change safe to attempt.

Scoped to the framing/smuggling surface this inventory covers. Strength is as

**MUST — violating these is non-conformance, and all four are unmet today**

| Obligation | Clause | Status |
|---|---|---|
| Invalid Content-Length → unrecoverable error | 9112 §6.3 r5 | ✗ reported as `.none` (A) |
| Chunked-not-final in a request → 400 + close | 9112 §6.3 r3 | ✗ frames as chunked (B) |
| Intermediary strips Content-Length when TE present | 9112 §6.3 r3 | ✗ not reportable (C) |
| Reject whitespace between field-name and colon | 9112 §5.1 | ⚠ unverified — F13 |

| obs-fold rejected/replaced in requests | 9112 §5.2 | ⚠ unverified — F15 |

**SHOULD / ought — dispositional, and the reason a "detected" condition still needs a decision**

| Obligation | Clause |
|---|---|
| TE+CL message "ought to be handled as an error" | 9112 §6.3 |
| Servers ought to bound field and body sizes | 9110 §5.4, 9112 |

**MAY — genuine implementation latitude**

| Latitude | Clause |
|---|---|
| Server may reject *or* honour TE alone when both present | 9112 §6.3 |
| Recipient may accept a bare LF as line terminator | 9112 §2.2 |

## §6. Recommendations `[DONE]`

Addressed to the HTTP-stack lane (placement) and the Lead (sequencing). Nothing
here has been acted on; this lane authored no source and created no packages.

### 6.0 The partition — fixable in place vs redesign

This is the planning cut. The three tiers differ in *blast radius*, not
difficulty, and that is what should drive sequencing.

| Tier | Findings | Change shape | Blast radius | Can proceed before the redesign? |
|---|---|---|---|---|
| **0 — crash, fix immediately** | **F** (two `fatalError` public entry points) | delete the two unimplemented `[Byte]` overloads, or give them a failure channel | deleting is source-breaking *only* for callers who cannot currently work — any live caller is already crashing | **Yes — ahead of everything.** Not a conformance item: shipped public API terminates the process |
| **1 — fixable in place, non-breaking** | **B** (chunked finality) | swap one call site to the finality accessor already shipping 9 lines away | none: no signature change, no new case, no consumer edit | **Yes — do it now.** Independently gateable |
| **2 — fixable in place, API-breaking** | **A** (invalid framing ⇒ `.none`), **C** (TE+CL unreported) | add a rejection outcome to `MessageBodyLength`; add a coexistence signal | ⚠️ **ecosystem-wide at each consumer's next resolve, undated** (§1.2). Every consumer's `switch` over the enum must gain a case | Yes, but **must be sequenced against the resolution fix** — see below |
| **3 — redesign; not fixable at any level of care** | **D** (exact consumed count), **E** (whole-buffer) | introduce an incremental parser contract: resumable state, need-more-bytes, exact consumed count, in-parse limits | new API surface; the framing layer is rewritten, semantics untouched | **No.** This *is* the redesign |

**Three consequences worth stating plainly:**

1. **Tier 1 should not wait for anything.** It is the only finding that is both a
   real security fix and free of blast radius. Holding it behind the redesign
   would be strictly worse for no gain.
2. **Tier 2 is gated on the resolution defect, not on HTTP work.** Adding a case
   to a published enum while consumers resolve at HEAD through an unversioned
   mirror map means the break arrives undated at each consumer's next resolve.
   The ordering that follows is: **fix resolution (R6) → then land Tier 2.**
   Doing Tier 2 first converts a security fix into a fleet incident.
3. **Tier 3 subsumes D.** D is not separately fixable: "track consumed bytes
   precisely" presupposes a consumed-count contract, and there is none to be
   correct against until E is addressed. Anyone planning D as its own task will
   discover this after starting.

**What this means for the build-vs-adopt call:** the split runs exactly along
this partition. Tiers 1–2 are *keep and repair* — the semantics layer is sound
and the framing defects are local. Tier 3 is *replace* — and it is confined to
the framing layer, leaving 9110's 5,916 lines of semantics untouched either way.

**R0 — THE GENERALISATION: a total signature over a partial operation.** This is
the single pattern that predicts the two worst findings, and it is worth more
than either of them individually.

- **Finding A**: `calculate(…) -> MessageBodyLength`, non-throwing, over an
  operation that *can* fail (invalid framing). Failure has nowhere to go, so it
  collapses into `.none` — a valid-looking answer.
- **Finding F**: `parse(_ data: [Byte]) -> Self`, non-throwing, over an
  operation that *can* fail (malformed line). Failure has nowhere to go, so the
  implementation traps.

Same root cause, two different symptoms — a wrong answer in one case, a crash in
the other. The lesson generalises past HTTP: **when a partial operation is given
a total signature, the failure does not disappear; it relocates to whichever
escape hatch is nearest.** Either a legal-looking sentinel or a trap.

**Use it as a search predicate, not just an explanation.** The productive audit
question for the rest of the chain is *"which non-throwing, non-Optional
functions can actually fail?"* — that query would have found A and F before
either was reported, and it is the recommended shape for the Step 3 audit.
The `try!` site at `HTTP.Request.swift:148` is the same family caught early:
harmless today only because its argument is a constant.

**R1 — Fix Finding B first among the conformance items.** One call site moves
from `hasChunked` (membership) to the finality accessor already shipping nine
lines away. Highest security-per-line-changed, non-breaking, independently
gateable. (Tier 0's Finding F is ahead of it, but is a deletion rather than a
conformance fix.)

**R2 — Treat Finding A as an API change, and sequence it deliberately.**
`MessageBodyLength` needs a rejection outcome distinct from `.none`; that is a
breaking change to a published type. ⚠️ **Per §1.2 it goes live ecosystem-wide at
each consumer's next resolve, with no version boundary.** Flagged individually
here rather than folded into a list, as §1.2 requires. This is the finding whose
*fix* is riskier than the finding.

**R3 — Split the build-vs-adopt verdict.** The tree is strong on **semantics**
(9110: 5,916 lines, and the harder half to get right) and structurally weak on
**framing** (9112: 3,002 lines, whole-buffer). Findings D and E are precisely
what mature socket-driven parsers must get right to function at all. "Keep and
extend the semantics; redesign the framing layer" may be a sharper cut than one
verdict over both. **Input to the HTTP lane's call, not a placement claim.**

**R4 — Range (9110 §14) is the largest semantic gap** and absent three ways
(§2.4b). It is not framing-critical, so it should not block N7 Phase 1, but it
will block any byte-serving consumer and interacts with §6.3 via 206 +
`Content-Range`.

**R5 — File the `HTTP.Cache` vocabulary trap** (§2.4c) as a namespace defect.
The law is substantial and correct; the obvious spelling silently reaches an
empty enum. Cheap to fix, and the kind of thing that costs a consumer an
afternoon.

**R6 — The unversioned-resolution defect is the most serious thing this
inventory touched, and it is not an HTTP problem** (§1.1). A 1,256-entry mirror
map with no version gate means any committed change to any package reaches
consumers undated at next resolve. It produced a fleet incident today that was
then misattributed to a rendering change. It appears unowned; recommend the Lead
assign it. **N7 will make this worse**, because HTTP types are broadly consumed.

**R7 — Adopt the two probe-defect controls fleet-wide** (§2.5). Both produce a
clean zero indistinguishable from true absence, and both have now invalidated
real censuses in this fleet — the 7230 census twice, in opposite directions.
