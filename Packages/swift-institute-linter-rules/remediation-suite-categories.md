# suite categories

**1,276 findings** — fifth-largest class in the fleet compliance ledger of 2026-08-02. Citation
`[TEST-005]`. Predicate:
[`Lint.Rule.Framework.SuiteCategories.swift`](../Sources/Institute%20Linter%20Rule%20Framework/Lint.Rule.Framework.SuiteCategories.swift).

Read [remediation-mechanics.md](remediation-mechanics.md) first.

---

## What the convention means

Every top-level test suite declares the same three nested sub-suites: `Unit`, `` `Edge Case` ``,
and `Integration`.

The recorded reason for holding to a **fixed** set is cross-package searchability: a fixed
vocabulary is what makes it possible to ask a question like "show me every integration test in
the ecosystem" and get an answer. A locally-invented fourth category defeats that for everyone,
which is why the remedy is never to add a category of your own.

Note what that rationale does and does not settle. It settles that the names are fixed and
shared. It does not, in the ecosystem's recorded guidance, define a precise boundary between the
three — so the working split below is offered as a working split, not as a recorded taxonomy,
and where a test genuinely sits on a line the choice is yours to make and to keep consistent
within the package.

`Performance` was required by earlier versions of this rule and was dropped on 2026-05-15:
performance work belongs in separate benchmark packages, not in the test framework. A
`Performance` sub-suite may still exist and passes the rule — extras never fire — but it is no
longer required, and adding one is not a remediation.

## What the predicate actually flags

It fires on a **top-level `@Suite struct`** that is missing any of the three canonical sub-suites
as nested **`@Suite struct`** members. The diagnostic names which are missing.

"Top-level" is the predicate's own definition, and it has one deliberate subtlety: an
`extension` ancestor is **transparent**. The house idiom —

```swift
extension Lint.Rule {
    @Suite struct `Compound Tests` { … }
}
```

— is in scope, because the extension is the declaration site rather than a reopening of an
unrelated namespace. A `@Suite struct` nested inside another **nominal type** (struct, class,
enum, actor) is out of scope; that nesting is genuine.

Only a nested **`@Suite struct`** counts as declaring a category. A nested `enum Unit`, a
`struct Integration` without the attribute, or a `typealias Unit` does not — the rule still
fires, and that combination is the trap described under step 2.

Backticked names are normalized before comparison, so `` `Edge Case` `` matches. Extras such as
`Performance` or `Snapshot` are ignored.

### One predicate limitation to know before you remediate, and one fixed

This produces findings, or the absence of findings, that the convention does not explain.

- **Category members inside `#if` are not counted.** The body scan reads the member block
  directly rather than splicing `#if` clauses, so a category declared inside a conditional reads
  as absent and the rule fires even though the category is there. Filed as
  [#47](https://github.com/swift-foundations/swift-institute-linter-rules/issues/47); the sibling
  `minimal type body` predicate does splice conditional members, and this one does not. Do not
  "fix" it by declaring a second copy outside the conditional — see step 2.

The other predicate limitation once documented here — the bare `@Suite` spelling being the only
one recognized, with the qualified `@Testing.Suite` spelling invisible to the rule — is fixed as
of [`e24b426`](https://github.com/swift-foundations/swift-institute-linter-rules/commit/e24b426fcaf81f11c54a0209e3b18b9d6a89a67c)
(landed via [#48](https://github.com/swift-foundations/swift-institute-linter-rules/pull/48),
closing [#45](https://github.com/swift-foundations/swift-institute-linter-rules/issues/45)).
`suiteCategoriesHasSuiteAttribute` now recognizes the qualified spelling at both call sites, the
rule gate and the declared-category collection, matching the `.Suite`-suffix handling this
package's other predicates already use. A package written with the qualified spelling now reports
findings, or their absence, on the same terms as the bare spelling.

### And one class of suite the rule never sees

Suites generated by the `#Tests` macro have no `@Suite struct` declaration in source at all — the
source carries a macro expansion, and the rule parses source. Those suites are invisible to this
rule in both directions, so a clean run over a `#Tests`-based test target is evidence that the
rule found nothing it can see, not evidence of compliance. Relatedly, the macro emits `EdgeCase`
where the hand-written convention uses `` `Edge Case` ``; do not normalize one spelling into the
other, because the macro emits its own.

## Step 1 — run the rewriter

This is the safest rewriter in the ledger, filed as
[#44](https://github.com/swift-foundations/swift-institute-linter-rules/issues/44). It appends
the missing categories, in canonical order, as empty `@Suite struct <Name> {}` members at the end
of the member block.

```sh
workspace package lint --package-path <package> --fix --dry-run
workspace package lint --package-path <package> --fix
```

It is purely additive: nothing is renamed, moved, or reworded, no existing member is touched, and
there is no call-site surface of any kind. The result is a suite tree with additional empty
suites, which the runner reports with zero tests.

**One prerequisite to check.** These findings live in test targets, and fix application is gated
on the declared SwiftPM target roots. The applying invocation must cover test target roots or
the rewriter reaches nothing — and reaching nothing looks exactly like having nothing to do.
Confirm the finding count actually fell.

### What the rewriter refuses

1. **A name collision with an existing member of any declaration kind.** The predicate counts
   only `@Suite struct` members, so a nested `enum Unit`, a non-`@Suite` `struct Integration`, or
   a `typealias` of that name leaves the rule firing while making the insertion a redeclaration
   error. This is the refusal that makes the rewriter safe rather than merely plausible.
2. **A member block containing `#if`**, or a suite declaration inside an `#if` clause — the
   insertion position becomes clause-dependent.
3. **A suite with direct `@Test` members in its own body.** Appending empty categories there
   would silence the rule while leaving those tests uncategorised: mechanically valid,
   semantically vacuous. This is the residual class that carries all the actual judgment.

## Step 2 — the decision tree for what remains

### The suite has direct `@Test` members in its own body

This is the finding worth caring about, and it is the only one in this rule that is real work.
The suite has tests; they are simply not in a category. Appending three empty categories beside
them would satisfy the predicate and accomplish nothing — which is precisely why the rewriter
declines to do it for you.

Classify each test and move it into the sub-suite it belongs to. As a working split:

| Category | Tests that belong there |
|---|---|
| `Unit` | The behaviour under ordinary, in-contract inputs. The bulk of most suites. |
| `` `Edge Case` `` | Boundaries and degenerate inputs: empty, zero, one, maximum, overflow, the first and last index, malformed input, the documented error paths. |
| `Integration` | Behaviour that depends on a boundary the unit cannot prove on its own — another module, a real file system or network, a composed pipeline of several components. A same-target test cannot establish a cross-module claim however green it is, and that is the distinction this category records. |

Move tests by placing them in an extension of the category, which is the house shape:

```swift
extension Cursor.Test.Unit {
    @Test func `advancing past the limit clamps`() { … }
}
```

If a category ends up with no tests, leave it declared and empty. The three are the fixed
vocabulary; an empty one is a true statement about the suite.

### An existing member collides with a category name

Something in the suite body is already called `Unit`, `Edge Case`, or `Integration` and is not a
`@Suite struct` — commonly a fixture enum or a helper type. You cannot declare the category
alongside it.

Decide which one should own the name. In nearly every case the category should, because the name
is reserved ecosystem vocabulary and the fixture's name is local. Rename the fixture to something
that describes it (`UnitFixture`, or better, something that says what it actually is), then
declare the category. Renaming a test fixture is a same-file or same-target change with a small,
fully-enumerable consumer set — check with cclsp and move on.

If the colliding declaration genuinely must keep the name, that is a suppression with a specific
reason.

### Categories are declared inside an `#if`

The categories exist; the predicate cannot see them
([#47](https://github.com/swift-foundations/swift-institute-linter-rules/issues/47)). Do **not**
add a second declaration outside the conditional — that is a redeclaration in whichever
configuration the `#if` is active.

The lawful shape is to declare all three categories unconditionally and confine the conditional
to the tests inside them:

```swift
@Suite struct `Kernel Tests` {
    @Suite struct Unit {}
    @Suite struct `Edge Case` {}
    @Suite struct Integration {}
}

#if canImport(Darwin)
extension Kernel.Test.Integration {
    @Test func `queue registers a filter`() { … }
}
#endif
```

This is better structure regardless of the rule: a category's existence is not
platform-dependent, only its contents are. Where that restructure is genuinely not possible, the
finding is a predicate limitation and a lawful suppression.

### The suite uses `@Testing.Suite`

As of [`e24b426`](https://github.com/swift-foundations/swift-institute-linter-rules/commit/e24b426fcaf81f11c54a0209e3b18b9d6a89a67c)
(closing [#45](https://github.com/swift-foundations/swift-institute-linter-rules/issues/45)),
the qualified spelling is recognized on the same terms as the bare `@Suite` spelling, at both
call sites. A finding here is a real finding, and a zero is real compliance — treat it exactly
as you would a bare-spelling suite. Do not respell attributes to make the rule fire either way.

### The plain case — categories simply missing

Add the missing ones, in canonical order, empty. This is what the rewriter does, and doing it by
hand before #44 lands is the same change:

```swift
@Suite struct Unit {}
@Suite struct `Edge Case` {}
@Suite struct Integration {}
```

Note the backticks on `` `Edge Case` ``. Without them it is not a valid identifier, and
`EdgeCase` is the macro's spelling, not this one.

## Worked examples

### Missing one category, no complications

`swift-witness-primitives`, `Tests/Witness Primitives Tests/Witness Tests.swift`:

```swift
extension Witness {
    @Suite
    struct Test {
        @Suite struct Unit {}
        @Suite struct `Edge Case` {}
    }
}
```

The house extension idiom, which the predicate treats as top-level. Diagnostic:
`Missing: Integration.` Remediation is one line:

```swift
extension Witness {
    @Suite
    struct Test {
        @Suite struct Unit {}
        @Suite struct `Edge Case` {}
        @Suite struct Integration {}
    }
}
```

Leave it empty. The suite has no integration tests, and an empty `Integration` is a true statement
about it — that is what a fixed vocabulary is for.

This is the plain case, it is the majority of the 1,276, and it is what the rewriter in
[#44](https://github.com/swift-foundations/swift-institute-linter-rules/issues/44) will do.

### Direct tests in the suite body — the residual case

`swift-percent-primitives`, `Tests/PercentTests/ReadmeVerificationTests.swift`:

```swift
@Suite("README Verification")
struct ReadmeVerificationTests {

    @Test("Quick Start example from README line 50-69")
    func quickStartExample() throws { … }

    …                                    // nineteen @Test functions in the body
}
```

Top-level `@Suite struct`, all three categories missing, and nineteen tests sitting directly in the
body. Appending three empty categories would clear the finding and leave all nineteen
uncategorised — mechanically valid, semantically vacuous, and exactly what the rewriter declines to
produce.

The remediation classifies each test. These are all verifications that documented examples still
compile and produce the stated results, which is a whole-README claim rather than a claim about one
function in isolation:

```swift
@Suite("README Verification")
struct ReadmeVerificationTests {
    @Suite struct Unit {}
    @Suite struct `Edge Case` {}
    @Suite struct Integration {}
}

extension ReadmeVerificationTests.Integration {
    @Test("Quick Start example from README line 50-69")
    func quickStartExample() throws { … }
}
```

with the arithmetic-identity and formatting tests going to `Unit`, and any rounding-boundary or
zero-denominator cases to `` `Edge Case` ``.

Two things worth noticing while you are in this file. The suite is a top-level `struct
ReadmeVerificationTests` rather than an extension of the source type, which is a separate
convention this rule does not check — and `ReadmeVerificationTests` is itself a compound type name,
so the file carries findings from more than one rule. Remediate one rule at a time; see
[remediation-mechanics.md §4](remediation-mechanics.md#4-batch-by-symbol-and-by-review-not-by-count).

### A collision

```swift
extension Codec {
    @Suite struct Test {
        enum Unit { case bytes, words }   // fixture, not a category
        @Suite struct `Edge Case` {}
        @Suite struct Integration {}
    }
}
```

Diagnostic: `Missing: Unit.` — correctly, since the `enum` is not a `@Suite struct`. Appending
`@Suite struct Unit {}` is a redeclaration error. Rename the fixture to what it is, then declare
the category:

```swift
extension Codec {
    @Suite struct Test {
        enum Granularity { case bytes, words }
        @Suite struct Unit {}
        @Suite struct `Edge Case` {}
        @Suite struct Integration {}
    }
}
```

## Suppression: the lawful shapes

Per [remediation-mechanics.md §3](remediation-mechanics.md#3-suppress-only-where-the-shape-is-lawful-and-always-with-a-reason).
This rule has few lawful suppressions, because in most cases the fix is three lines and free:

```swift
// swift-linter:disable:next suite categories
// REASON: the three categories are declared inside the `#if canImport(Darwin)`
// clause below; the rule's body scan does not splice `#if` members, so they
// read as absent (swift-institute-linter-rules#47). Declaring them
// unconditionally is not possible here because the enclosing suite is itself
// platform-gated.
@Suite struct `Kernel Tests` { … }
```

```swift
// swift-linter:disable:next suite categories
// REASON: `Integration` here is the name of the specification's own conformance
// level, fixed by the spec's vocabulary; it cannot be renamed, and the category
// cannot be declared beside it.
@Suite struct `Conformance Tests` { … }
```

These do **not** qualify: "this suite has no integration tests" — declare the empty category,
that is what it is for; "the categories add noise"; "we use a different taxonomy in this
package" — a local taxonomy is the specific thing the fixed set exists to prevent.

**Adding a `Performance` or `Snapshot` sub-suite is not a remediation.** Extras never made the
rule fire, so adding one changes nothing about the finding.

## Verification

Per [remediation-mechanics.md §5](remediation-mechanics.md#5-verify-per-finding-and-verify-the-whole-file):

```sh
workspace package lint  --package-path <package>
workspace package test  --package-path <package>
```

The test run matters more here than the build. Two rule-specific checks:

- **Confirm the tests still run.** Moving a test into a category changes its suite path. The
  hazard the testing guidance records is that a suite in the wrong shape can compile and be
  **silently never discovered** — nothing fails, the tests simply do not execute. Compare the
  test count before and after; an unchanged pass count with a fallen test count is the signature.
- **Confirm the count fell by one per suite, not one per category.** This rule reports **one
  finding per suite**, listing all missing categories in a single diagnostic. A suite missing all
  three contributes one finding, not three.

## Honest limitations

- The rewriter and this playbook satisfy the predicate — that three named suites exist. Neither
  can tell whether a test is in the **right** category. Category membership is a claim the rule
  checks the shape of and not the truth of.
- The `@Testing.Suite` blind spot ([#45](https://github.com/swift-foundations/swift-institute-linter-rules/issues/45))
  is fixed as of [`e24b426`](https://github.com/swift-foundations/swift-institute-linter-rules/commit/e24b426fcaf81f11c54a0209e3b18b9d6a89a67c);
  this rule's zero is now a statement about both spellings, not the bare one only.
- The `#if` non-splice ([#47](https://github.com/swift-foundations/swift-institute-linter-rules/issues/47))
  cuts the other way: it makes the count too high rather than too low, since a suite whose
  categories are conditional fires despite being compliant. Some share of the 1,276 is that false
  positive, and the share is not knowable until #47 lands.
- `#Tests`-generated suites are outside the rule's sight entirely, so the ledger count for this
  rule under-reports the true population of uncategorised suites by however many packages use the
  macro.
